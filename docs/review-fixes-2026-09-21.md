# 2026-09-21：修正交易卡住、同步漏查與帳戶追蹤

這次先修六個會影響使用流程的問題，包含交易失敗後無法繼續、加速成功卻還在等待，以及重啟後停止追蹤帳戶。也補上 RPC 回應大小限制，避免異常回應吃掉過多記憶體。

| 原本會遇到的問題 | 現在怎麼處理 | 怎麼確認 |
| --- | --- | --- |
| Solana 暫時回報失敗，就開放下一筆付款 | 等到 finalized，也就是交易結果已確定，才解除等待限制 | 測試 processed／confirmed 失敗後，最後成功與最後失敗兩種情況 |
| 一直查舊紀錄，新交易遲遲查不到 | 每輪批次查最多 256 個簽名，輪流處理；其中一輪失敗也不會每次從頭重來 | 放入 600 筆紀錄，讓第一輪 RPC 失敗，確認後續仍查得到所有紀錄和最新付款 |
| 兌換時輸錯密碼，關閉視窗後就卡住 | 後端確定這筆報價還沒有交易落盤時，回傳 `send_rejected`，讓畫面可以重新預估；結果不明的交易仍保留追蹤 | 錯誤密碼、找不到報價、重新整理，以及重試同一筆報價 |
| 加速交易成功，畫面還在等舊交易 | 更新進度時重新查紀錄，沿著 `replacedBy` 找實際收錄的交易；取消交易不會被當成兌換成功 | 加速、取消、加速取消交易，以及內容不同的替代交易 |
| 發現的代幣太多，手動同步直接失敗 | 每批最多 20 個合約，全部成功才移到下一個區塊；中途失敗就保留原起點 | 22 個合約拆成 20 + 2，讓第二批失敗後再重試；起始區塊留空也不會漏掉先前範圍 |
| 重啟後，必須有人開帳戶頁才恢復背景追蹤 | 啟動時就載入已登記帳戶；網頁和 faucet 共用同一組服務，避免重複開啟錢包 | 不開頁也能繼續掃描，封存帳戶同樣有效；之後開頁和啟用 faucet 也不會撞到檔案鎖 |

## RPC 的兩項補強

Solana 查詢失敗時，原本會直接把 SDK error 寫進 log；這類錯誤可能包含 RPC URL，連同 URL 裡的 API key 一起被記錄。現在改用固定的錯誤訊息，仍看得出是哪個查詢失敗，但不帶出端點內容。

ERC-4337 的三個 RPC 入口都經過 `Client.call`。現在會先檢查回應大小，超過 **2 MiB** 就拒絕；HTTP 錯誤頁也不再讀入或原樣顯示。JSON 回應還必須符合 2.0 格式、對上這次請求的 ID，而且只能有 result 或 error 其中一種結果。

測試涵蓋超大串流、超大的合法 JSON、HTTP 錯誤、錯誤 ID／版本、缺少結果、同時帶有結果與錯誤，以及多接一段 JSON。原有的正常送出、Gas 估算、等待收據和 AA error 測試也一起跑過。

## 測試結果怎麼看

Go 測試使用可丟棄的離線容器。程式和套件快取只能讀取，測試只能寫入自己的暫存資料與結果目錄：

```sh
go test -race -count=1 ./...
go vet ./...
gofmt -l cmd internal contracts tests
go fix -diff ./...
```

瀏覽器測試使用本機假 API，外部請求會被攔截。端到端測試則用暫存錢包和模擬 EVM，確認錯誤密碼會被拒絕，之後能存入 0.05 ETH、取回 0.02 ETH，並核對兩筆成功收據與剩餘 0.03 ETH：

```sh
npm test --prefix tests/browser
RUN_BROWSER_E2E=1 go test -race -count=1 -v -run '^TestE2EVaultBrowser$' ./tests/e2e
```

上面都是本機或模擬測試，沒有送出 public Sepolia 交易。推送後的 CI 與部署結果，請以該 commit 的 GitHub Actions 紀錄為準。
